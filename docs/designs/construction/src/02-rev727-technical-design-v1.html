1. Purpose and scope

Darkan already contains a complete 2012-style house: a grid of purposeful rooms with furniture hotspots, about 6,000 lines of Kotlin and Java. This document designs the change from that system to the RS3 free-placement model described in document 1, on the unmodified revision-727 client.

1.1 Goals

  • Rooms are shapes without purpose; furniture is placed on any valid tile and can be moved, rotated and returned to storage without loss.
  • The craft → store → place loop: workbench crafting, a furniture trunk, a build-mode placement session.
  • The RS3 limits: 48×48 plot, 25 rooms, a level-scaled furniture cap, 12 room shapes, Construction to level 120.
  • Existing player houses survive: legacy rooms and furniture are migrated, not discarded.

1.2 Non-goals for the first releases

  • RS3 rendering, models, animations and lighting. The client is revision 727 and stays so.
  • Homesteads (shared multi-house neighbourhoods): deferred to a later phase (section 12).
  • 45° rotation and drag-and-drop, which the 727 client cannot express (section 6.4).
  • Replicating all 650+ RS3 decorative items. The first catalogue is the existing 447 house objects.
Reading guide. VERIFIED means checked in this repository (code or cache). DESIGN-style statements are decisions or proposals. OPEN means unresolved and listed in document 3. Tags in document 1 describe RS3 facts only.

2. Baseline: how the current house works

Everything below was checked in the repository on 2 October 2026 (paths relative to server/).

2.1 Rendering

  • A house is an 8×8-chunk instance (Instance.of(tile, 8, 8)). A chunk is 8×8 tiles. VERIFIED
  • Each room is one chunk copied from a template map (regions 29_79 and 30_79 in cache-source/maps) with one of four rotations, by Instance.copyChunk(...) built on InstanceBuilder. VERIFIED
  • The client is sent a chunk-descriptor array naming, for every chunk of a 13×13 window on 4 planes, which template chunk to draw: (rot&3)<<1 | (plane&3)<<24 | (chunkX&0x3ff)<<14 | (chunkY&0x7ff)<<3, or −1 for none (core/.../ServerRegionPackets.kt). VERIFIED The client loads terrain and base objects itself; the server sends only object deltas.
  • Rooms may not sit on grid row/column 0 or 7, so the usable grid is 6×6 chunks = 48×48 tiles, exactly the RS3 plot. VERIFIED
  • Planes: 0 dungeon, 1 ground floor, 2 upper floor, 3 roofs. House styles pick the source plane/region of the template. VERIFIED

2.2 Furniture

  • Template chunks contain hotspot locs (option 5 "Build"). Building swaps the hotspot for the furniture loc on the same tile and rotation, so the template alone fixes position. The save stores only (build, slot) per room. VERIFIED
  • Content tables: HouseObjects (447 entries), HouseBuilds (~128), HouseRooms (25), with raw legacy ids that break the project's no-magic-numbers rule. VERIFIED
  • The furniture-create interface (1306, 7 slots) and its client script poh_furniture_create already read cost and level from object params. VERIFIED

2.3 Persistence and lifecycle

  • The save is Gson JSON in Mongo. Serialised House fields: rooms, location, look, buildMode, servants, pets and others. Enums serialise by name. VERIFIED
  • Adding, removing a room or toggling build mode runs refreshHouse(): destroy and recreate everything behind a loading screen. Furniture builds touch only objects. VERIFIED

5. Spatial model

{{GRID_SVG}}

5.1 Coordinates

  • The instance stays 8×8 chunks. Border cells (index 0 and 7) are the unusable black chunk; interior cells (1–6) form the plot.
  • Furniture position is stored as plot-relative tiles: x, y in 0..47, plane 1 or 2. Tile (x, y) lies in cell (1 + x/8, 1 + y/8). This makes saves independent of where the engine allocates the instance.
  • Rotation is 0–3 clockwise, the loc rotation the client understands.

5.2 Floors

Plane 1 is the ground floor and plane 2 the upper floor, as today. An upper-floor room must sit above a ground-floor room. Plane 0 is reserved for the legacy dungeon (section 11) and stays empty in the first release. Plane 3 carries roofs, drawn only outside build mode.

5.3 Room shapes as chunk cells

A chunk is the smallest unit the client can be told to draw from a template, so every room occupies a whole number of cells. Sub-chunk shapes (4×4, 4×8, 4×16) are drawn as a smaller room inside a full cell whose remainder is solid and walled off.

ShapeRS3 footprintCellsTemplateWaste
Square8×81×1full-cell shell0%
Square (large)16×162×2four shell chunks, centre walls removed0%
Hallway (large)8×161×2two shell chunks0%
Hallway4×81×1centred 4-wide strip50% of cell

Square (small)4×41×1centred 4×4 shell75% of cell

Every shape places its doorways at the midpoint tiles (3 and 4) of each cell edge, so any two adjacent cells can be joined and a cell-embedded small room reaches the edge through a short vestibule. OPEN Whether the real RS3 grid snaps at 4 tiles (document 1, section 4.4) is unknown; if it does, 4-wide rooms would pack two to a cell in RS3 but not here. This is the largest fidelity loss in the design, and it is accepted for the first release.

The RS3 rule that disconnected rooms must be 2 tiles apart is dropped: adjacent cells are separated by their own walls, and a cell with no room is simply black.

5.4 Capacity check

The plot holds 36 cells per floor. Twenty-five one-cell rooms fit with 11 cells to spare. The largest case (a 2×2 large square) uses 4 cells; a house of mixed large rooms reaches the 25-room cap before running out of cells, so cells are never the binding limit.

6. Rooms and shells

6.1 Shell versus legacy room

A shell is a template chunk containing only structure: floor, outer walls, doorway gaps and non-interactive trim. It has no hotspots and no purpose. The legacy templates in regions 29_79 and 30_79 mix structure and hotspots, so they cannot be used unchanged.

6.2 Two-stage template strategy

  1. Bootstrap. Reuse the legacy Garden or Parlour chunk as the Square shell and delete every hotspot base object when the chunk is applied (the visit-mode code already removes hotspots this way). This gives a working Square room with no new assets and proves the pipeline.
  2. Authoring. Build dedicated shell chunks for the remaining shapes and styles by editing terrain.json and locs.json under cache-source/maps, following the allocate-at-end-of-index and read-back rules of the content workflow. Shapes that cut away floor (octagon, rounded) need new underlay/overlay terrain, not just objects.

6.3 Styles

The existing mechanism selects the source plane and region by a style index (7 values today). The five RS3 styles map onto this: Basic Wood, Basic Stone, Fancy Stone and Fremennik Wood have 727 equivalents; Dark Stone has none and must be authored. OPEN Styles are per room, which matches the RS3 "mixed styles" behaviour.

6.4 Doorways

Each cell edge has one doorway of two tiles. A doorway is in one of three modes: open (default; no wall object), wall or window (a wall object spawned over the gap). Two adjoining rooms share a doorway and the stricter mode wins. Upper-floor doorways may not be open to void: if the neighbour cell is empty the mode is forced to wall or window, matching RS3's "cannot be left empty" rule.

7. Furniture model

7.1 Catalogue entry

FurnitureDef(
  id            : String          // stable save key, snake_case, never renamed
  category      : FurnitureCategory
  loc           : Loc gameval     // the built object
  icon          : Obj gameval     // item shown in trunk and workbench
  placement     : FLOOR | WALL | WALL_DECOR | GROUND_DECOR | SURFACE
  footprint     : (sizeX, sizeY)  // taken from the object definition
  craftLevel    : Int
  xp            : Double
  materials     : List<Material>
  workbenchTier : WOODEN | STEEL | REINFORCED
  perHouseCap   : Int?            // cauldron 5, nexus 1, and so on
  onUse         : handler key?    // functional furniture
)

The first catalogue is generated from the 447 existing HouseObjects entries. One difficulty: those entries list loc ids per hotspot variant (rugs, windows, seating have several), index-aligned to HouseBuilds.ids. The conversion picks the canonical variant by footprint and records the rest as aliases. OPEN Some locs encode orientation or corner handedness that the hotspot used to supply; each such object needs a manual check.

Per the project rules every id is a gameval constant, and any asset we add is named for its purpose in the catalog, not a placeholder.

7.2 Occupancy and slots

The engine tracks one object per slot per tile (wall, wall decoration, scenery, ground decoration), clips collision through GameObjectCollision, and emits chunk deltas. VERIFIED Placement classes map directly onto slots:

ClassSlotTypical objectsRule
FLOORscenerytables, beds, rangesall footprint tiles free of scenery, not wall-blocked
GROUND_DECORground decorationrugsslot free; does not block FLOOR objects above it
WALL / WALL_DECORwall / wall decorationwindows, paintingstile has an interior wall on the chosen side; slot free
SURFACEscenery (offset)vases, bookstile covered by a surface-flagged object

OPEN Whether a multi-tile scenery object claims the scenery slot on every covered tile or only its base tile must be read from Chunk.spawnObject; the validator depends on it.

7.3 Validation

validate(def, tile, rot, plane):
  cells = footprint(def.sizeX, def.sizeY, rot) at tile
  for t in cells:
      require t inside plot and covered by a placed room's floor mask on plane
      require t not in a doorway keep-clear zone or on the entry portal tile
  match def.placement:
      FLOOR        -> all t: scenery slot free, shell does not block t
      GROUND_DECOR -> all t: ground-decor slot free
      WALL, WALL_DECOR -> adjacent shell wall on facing side, slot free
      SURFACE      -> all t covered by a surface-flagged FLOOR object
  require placedCount(layout) < furnitureLimit(constructionLevel)
  require perHouseCount(def) < def.perHouseCap
  require doorways and portal remain reachable (flood fill on the room mask)

Validation runs twice: for the ghost preview, and again at commit time on the world thread, because the world may have changed between the click and the confirm.

8. Rendering and lifecycle

8.1 From rebuild-all to incremental

Today every room change destroys and recreates the whole instance. Under free placement that is unacceptable: moving one table must not reload the house. The new renderer works at three granularities:

ChangeWorkClient impact
Place, move, remove furnitureSpawn/remove one object, update collisionObject delta only
Doorway modeSpawn/remove wall objects on 2 tilesObject delta only
Add, remove, move, restyle a roomcopyChunk for the affected cells, then reapply their furnitureMap reload for displaced players
Enter / leave build modeToggle roofs and ghost tooling; no copyNone

InstanceBuilder.publish already forces a map reload for players standing on a replaced chunk, VERIFIED so a room change in a populated house works without extra code. A player inside a removed room is teleported to the portal first.

8.2 Build order when a house loads

  1. Reserve the instance (after the chunkIds fix in section 2.4).
  2. For every cell, copy the shell chunk for its room, shape, style and rotation, or the black chunk.
  3. Strip hotspots and other template objects the shell flags as removable.
  4. Apply doorway modes.
  5. Spawn every placed furniture object, most-recently-placed last, and clip it.
  6. Spawn roofs when not in build mode; place players.

The object count is small: at most 500 furniture plus a few dozen doorway objects. The shell's thousands of base objects live in the client's own map data and cost the server nothing.

8.3 Concurrency

Chunk copies are asynchronous and complete on the world thread. The house carries a single operation lock: while a copy is in flight further structural edits are refused with a short message, and furniture operations on the affected cells queue behind it.

9. Interaction

9.1 Placement session

{{FLOW_SVG}}

The client has no hover, drag or wheel events, so the RS3 live-preview experience is replaced by a short explicit session:

  1. The player picks an item in the trunk interface (or "Move" on a placed object). The server opens a placement session bound to the player, with the item and rotation 0.
  2. The next ground click arrives as a Walk packet carrying the target tile. WalkHandler checks for an active session first and, if present, routes the click to it instead of storing a walk request. VERIFIED that the handler currently only stores the request; the hook itself is new and lives in the world module.
  3. The server runs validation and spawns a ghost visible only to that player. It is recoloured valid or invalid through the object mesh modifier. OPEN A per-player spawn packet and per-object recolour have not yet been confirmed in the code (document 3, O5); the fallback is a world-visible ghost that other players see briefly.
  4. Buttons on a small control interface: rotate left, rotate right, confirm, cancel. Clicking another tile re-targets the ghost.
  5. Confirm re-validates, commits (spawn, clip, persist, decrement the trunk), and ends the session.

Cancelling, logging out, leaving build mode, teleporting or taking any locking action clears the ghost and the session.

9.2 Move, swap and remove

  • Move: a right-click option on a placed object starts a placement session pre-loaded with that object; on confirm the old placement is removed in the same operation.
  • Swap: moving onto an occupied tile with a compatible footprint swaps the two objects (both re-validated at their new tiles).
  • Remove: a right-click option returns the item to the trunk with no loss.

Client state follows the project's varbit rule: a varbit only where the interface must own or refresh the value itself (for instance an "active session" flag), written to the first free bit of the feature's parent varp after listing every varbit on that varp. Server-only state, such as the layout itself, stays in the player save.

9.4 Crafting and XP

  • The workbench is an object with a tier. Outside the Rimmington portal a furniture workbench and trunk box are spawned at start-up; crafted in-house workbenches follow the wooden/steel/reinforced tiers.
  • Crafting consumes materials, checks level, grants XP, and adds one unit to the trunk. Placement itself needs no level (as in RS3 after Day 2).
  • Level 120: Skills.getLevelForXp and the level-to-XP table become skill-specific caps, Construction joining Dungeoneering at 120. The same formula gives level 120 at 104,273,167 XP, which supersedes the unreliable "200M" figure in document 1. OPEN Whether the 727 stats interface displays a virtual level above 99 for a skill other than Dungeoneering needs a client-script check.

9.5 Functional furniture

The existing HouseController already dispatches clicks on built-object ids (portals, fireplaces, larders, lecterns, stairs, doors and more) in a long chain. Because furniture keeps its loc id after placement, these handlers keep working; they are re-expressed as @ServerStartupEvent plugins keyed by catalogue entry and stripped of any assumption about the room the object stands in. Genuinely room-dependent handlers (stairs between floors, the entry portal) become required fixtures with their own placement rules.

New RS3 functional furniture (portal nexus, potion cauldron, tiered altars) is added after the core loop ships (section 12).

10. Persistence and migration

10.1 Schema

HouseLayout(
  version   : Int = 2,
  rooms     : List<PlacedRoom>,        // shape key, cellX, cellY, plane, rotation, style
  furniture : List<PlacedFurniture>,   // id, x, y, plane, rotation   (tiles 0..47)
  doorways  : Map<String, DoorwayMode>,
  storage   : Map<String, Int>         // furniture id -> count in the trunk
)

All keys are stable strings, never enum ordinals and never renamed, so a catalogue change cannot corrupt saves. The layout is a new nullable field on House; the legacy fields stay read-only until the migration is proven.

10.2 Legacy migration

Unlike RS3, which discarded layouts, the 727 house can keep them, because its legacy grid is the new cell grid:

  1. Each legacy RoomReference becomes a Square PlacedRoom at the same cell, plane and rotation, with the same style. Legacy room kinds that were not squares in spirit (the dungeon rooms, staircase chunks) are handled separately (section 11).
  2. Each legacy ObjectReference(build, slot) is resolved to a position by scanning the room's template chunk for the hotspot whose id is in build.ids, applying the room rotation. The result is a PlacedFurniture at that exact tile. Builds covering several hotspots (windows, floors, hedging) produce one object per hotspot.
  3. Any build with no catalogue mapping goes to the trunk as a refund unit and is logged for support.
  4. The migration runs once at login, writes the new layout, and keeps a snapshot of the legacy fields so it can be rolled back.

Servants, pets and the portal location carry over unchanged.
