1. Purpose and scope

Darkan already contains a complete 2012-style house: a grid of purposeful rooms with furniture hotspots. This document designs the change from that system to the RS3 free-placement model of document 1, on the unmodified revision-727 client.

1.1 Goals

  • Rooms are shapes without purpose; furniture is placed on any valid tile and can be moved, rotated and returned to storage without loss.
  • The craft → store → place loop: workbench, furniture storage, build-mode placement session.
  • The RS3 limits: 48×48 plot, 25 rooms, a level-scaled furniture cap (25 to 500), up to three floors, 12 room shapes, Construction to level 120.
  • Existing player houses survive: legacy rooms and furniture are migrated.

1.2 Non-goals for the first releases

  • RS3 rendering, models and animation. The client stays revision 727.
  • Homesteads, deferred to a later phase (section 12).
  • 45° rotation, drag-and-drop and a live cursor preview, which the 727 client cannot express (section 3).
  • Balconies with beam supports, and all 650+ RS3 decorative items. The first catalogue is the existing 447 house objects.
Reading guide. VERIFIED means checked in this repository (code or cache) during this work. OPEN means unresolved and tracked in document 3. Everything else is a design decision.

2. Baseline: how the current house works

All of this was checked in the repository on 2 October 2026 (paths relative to server/).

2.1 Rendering

  • A house is an 8×8-chunk instance. A chunk is 8×8 tiles. Each room is one chunk copied from a template map (regions 29_79 and 30_79 in cache-source/maps) with one of four rotations, by Instance.copyChunk on top of InstanceBuilder. VERIFIED
  • The client is sent a chunk-descriptor array: for every chunk of a 13×13 window on 4 planes, which template chunk to draw, as (rot&3)<<1 | (plane&3)<<24 | (chunkX&0x3ff)<<14 | (chunkY&0x7ff)<<3, or −1 (ServerRegionPackets.kt). The client loads terrain and base objects itself; the server sends only object deltas. VERIFIED
  • Rooms may not sit on grid row/column 0 or 7, so the usable grid is 6×6 chunks = 48×48 tiles, exactly the RS3 plot. VERIFIED
  • Planes today: 0 dungeon, 1 ground, 2 upper, 3 roofs. Styles pick the template plane/region. VERIFIED

2.2 Furniture and content tables

  • Template chunks hold hotspot locs; building swaps the hotspot for the furniture loc on the same tile and rotation. The save stores only (build, slot) per room. VERIFIED
  • HouseObjects has 447 entries (395 distinct item ids, 812 distinct loc ids); HouseBuilds has 128 builds. All 395 items exist in config_obj, so every piece has a trunk icon. VERIFIED
  • Furniture-create interface 1306 (7 slots) and its client script already read cost and level from object params. VERIFIED

2.3 Persistence and lifecycle

  • Saves are Gson JSON in Mongo. Enums serialise by name. VERIFIED
  • Adding or removing a room, or toggling build mode, runs refreshHouse(): destroy and recreate everything behind a loading screen. VERIFIED

5. Spatial model

{{GRID_SVG}}

5.1 Coordinates

  • The instance stays 8×8 chunks; border cells (index 0 and 7) are the unusable black chunk and interior cells (1–6) form the plot.
  • Furniture position is stored as plot-relative tiles, x, y in 0..47, plus a floor index. The incoming Walk packet gives an absolute world tile and no plane (VERIFIED); the session converts it with the instance base and uses the player's own plane.
  • Rotation is 0–3, the loc rotation the client understands.

5.2 Floors and planes

RS3 allows three floors (first floor at level 30, second at level 70). The 727 client has four planes, and the roof needs the plane above the top floor, so three floors plus a roof need all four planes and displace the legacy dungeon on plane 0.

PhasePlane 0Plane 1Plane 2Plane 3
While the legacy dungeon existsdungeongroundfirst floorroofs
After the dungeon is retiredgroundfirst floorsecond floorroofs

So the first release supports two floors, which matches RS3 up to level 69, and the third floor ships with the dungeon's retirement. OPEN Decision D6.

Stairs follow RS3: a per-room "Add Stairs" option (level 30) that places a spiral staircase in the centre of the room and creates a room of the same shape above it, at double cost. The staircase is part of the room's shell variant, not free furniture, so room shapes need a with-stairs variant. Balconies with beam supports are out of scope.

Every shape puts its doorways on tiles 3 and 4 of each cell edge. This matches the legacy templates: VERIFIED each door side holds two door-hotspot locs on tiles 3–4, walls sit on tiles 1, 2, 5, 6 and corners on 0 and 7, and a closed side has walls on 3–4.

5.4 The largest fidelity loss: tile-granular rooms

Document 1 now establishes that RS3 builds on the game-square grid and requires separated rooms to be at least 2 tiles apart. That implies rooms can sit at tile offsets. The 727 client can only be told to draw a template at chunk (8-tile) offsets, so here every room snaps to an 8-tile cell. Consequences:

  • A 4-wide room cannot sit flush against another room's wall at a 4-tile offset; it is centred in its cell.
  • Rooms cannot be placed with 2-tile gaps; adjacent cells are separated by their own walls.
  • Layouts that rely on odd offsets (for example an L of 4-wide hallways) take more space.

An alternative would build floors and walls purely from spawned objects over a blank template, which allows tile offsets but costs thousands of objects per floor and loses terrain variety. It is rejected for the first release. OPEN Decision D8.

5.5 Capacity

The plot holds 36 cells per floor. Twenty-five one-cell rooms leave 11 spare, and large rooms hit the 25-room cap before running out of cells, so cells are never the binding limit.

6. Rooms and shells

6.1 Shell versus legacy room

A shell contains only structure: floor, outer walls, doorway gaps, non-interactive trim. The legacy templates (816 hotspots across 25 rooms) mix structure and hotspots, so they cannot be used unchanged.

6.2 Template facts

  • terrain.json stores tiles[level][localX] as a string of 64 tiles, each a comma-separated list of tokens: o<id>/<shape>/<rot> overlay, s<flags>, u<id> underlay, h<height>, or -. VERIFIED
  • locs.json entries are {id, x, y, level, shape, rotation}, region-local. VERIFIED
  • Every overlay in both regions has shape 0, so all legacy floors, even the throne room and chapel, are full squares; no existing chunk can be a shaped shell. VERIFIED
  • Void tiles are legal: a tile of h30 alone is valid, and the black chunk is 64 tiles of o143/0/0,s5,h30 with no locs. So cut-away corners and unused cell areas can be authored. VERIFIED That a void tile renders and blocks correctly in the client is still to be seen. OPEN
  • Styles differ only in floor overlay and wall/rock loc ids; layout is identical. VERIFIED

6.3 Template generation

Because styles change only ids, shells should be generated, not hand-built:

  1. Author one master shell per shape (12 shapes, with and without stairs) by editing terrain and locs.
  2. A generator script emits the style variants by substituting the wall and rock loc ids and the floor overlay id into a dedicated template region (or regions) in cache-source/maps.
  3. The catalogue maps (shape, wall style, floor style, stairs) to a template chunk.

The combinatorics need care: 12 shapes × 2 stair variants × 5 wall styles × 14 floor styles is 1,680 chunks, about 26 regions. Bootstrap with a small set (Basic Wood, three floors) and grow it. Floor style must be baked into terrain; wall style could instead be applied at runtime by replacing wall objects, which would cut the matrix to 12 × 2 × 14. OPEN Decision D7.

6.4 Bootstrap

Reuse the legacy Garden or Parlour chunk as the Square shell and delete every hotspot base object when the chunk is applied (visit mode already removes hotspots this way). That gives a working Square room with no new assets and proves the pipeline before any terrain is authored.

6.5 Doorways

Each cell edge has one doorway of two tiles in one of three modes: open (default; no wall object), wall, or window (a wall object spawned over the gap). Connected doorways are always open. Upper-floor unconnected doorways may not be open, matching RS3. The wall ids per style come from the map, not from WALL_IDS (defect in section 2.4).

7.2 Surface placement

Loc definitions carry modelSizeX/Y/Z (resize) and offsetX/Y/Z (translate), with offsetZ the height. VERIFIED A "table-top" variant of a vase or book is a new loc definition with a height offset. New locs are authored by adding a JSON file; ids 73902–73983 (82) fit in the existing archive, and anything above needs a new archive line in the index. VERIFIED Surface items therefore compete with other new content for 82 ids, so a new archive should be planned.

7.3 Occupancy

The engine tracks one object per slot per tile (wall 0, wall decoration 1, scenery 2, ground decoration 3), and a multi-tile object is stored under its base tile only; collision covers the full footprint with sizes swapped for rotations 1 and 3. A spawn into an occupied slot replaces the existing object, matching only on base tile and slot, so two overlapping multi-tile objects on different base tiles coexist. There is no helper that lists the objects covering a tile. VERIFIED

The chunk therefore cannot be asked "is this tile free?". The layout keeps its own occupancy index, a map from (floor, x, y, slot) to placed-object id, with every footprint tile expanded, rebuilt from the saved layout on load and updated on every change. All validation reads that index, and the renderer never spawns into a slot the index says is taken.

7.4 Validation

validate(def, tile, rot, floor):
  cells = footprint(def.sizeX, def.sizeY, rot) at tile
  for t in cells:
      require t inside plot and under a placed room's floor mask on floor
      require t not in a doorway keep-clear zone or on the entry portal tile
  match def.placement:
      FLOOR        -> all t: index.free(floor, t, SCENERY), shell does not block t
      GROUND_DECOR -> all t: index.free(floor, t, GROUND_DECOR)
      WALL, WALL_DECOR -> adjacent shell wall on facing side, slot free
      SURFACE      -> all t covered by a surface-flagged FLOOR object
  require count(layout) < furnitureLimit(constructionLevel)
  require perHouseCount(def) < def.perHouseCap
  require doorways and portal remain reachable (flood fill on the room mask)

It runs twice: for the ghost, and again at commit on the world thread.

8. Rendering and lifecycle

8.1 From rebuild-all to incremental

ChangeWorkClient impact
Place, move, remove furnitureSpawn/remove one object; update index and collisionObject delta only
Doorway modeSpawn/remove wall objects on 2 tilesObject delta only
Add, remove, move, restyle a roomcopyChunk for the affected cells, then reapply their furnitureMap reload for displaced players
Enter / leave build modeToggle roofs and tooling; no copyNone

InstanceBuilder.publish forces a map reload (setForceNextMapLoadRefresh then loadMapRegions) for players standing on a replaced chunk, VERIFIED so a room change in a populated house needs no extra code. A player inside a removed room is teleported to the portal first.

8.2 Build order when a house loads

  1. Reserve the instance (after the chunkIds fix).
  2. For every cell, copy the shell chunk for its room, shape, styles and rotation, or the black chunk.
  3. Strip hotspots and other flagged template objects.
  4. Apply doorway modes.
  5. Rebuild the occupancy index; spawn and clip every placed object.
  6. Spawn roofs when not in build mode; place players.

The server-side object count stays small: at most 500 furniture plus a few dozen doorway objects. The shell's base objects live in the client's own map data.

8.3 Concurrency and roofs

Chunk copies are asynchronous. The house carries one operation lock: structural edits are refused while a copy is in flight, and furniture operations on the affected cells queue behind it. The single legacy roof chunk fits only square rooms, so roofs are hidden for non-square shapes in the first release. OPEN (document 3, O9)

9. Interaction

9.1 Placement session

{{FLOW_SVG}}
  1. The player picks an item in the build interface (or "Move" on a placed object). The server opens a placement session bound to the player.
  2. The next ground click arrives as a Walk packet: Walk(x, y, forceRun, minimap), an absolute world tile, no plane. WalkHandler currently calls stopAll() and stores walkRequest, which Entity.processEntity consumes each tick. The session check goes before stopAll(). VERIFIED The server also sends MinimapFlag(255, 255) to clear the flag, since the client may draw its own. OPEN (O1b)
  3. The server validates and shows a ghost to that player only: player.packets.sendAddObject draws it, and sendCustomizeObject on a throwaway object with modifyMesh() recolours it (valid or invalid). VERIFIED These packets do not touch chunk state, so a chunk resend can overwrite the ghost; the session re-sends it after any map reload. A tile marker (sendSpotAnim or a hint icon) is available as a second cue.
  4. Buttons on a small control interface: rotate left, rotate right, confirm, cancel. Clicking another tile re-targets the ghost.
  5. Confirm re-validates, commits (spawn, clip, persist, decrement storage), and ends the session.

Cancelling, logging out, leaving build mode, teleporting or any locking action clears the ghost and the session.

9.2 Move, swap and remove

  • Move: a right-click option on a placed object starts a session pre-loaded with it; on confirm the old placement is removed in the same operation.
  • Swap: moving onto an occupied tile with a compatible footprint swaps the two objects, both re-validated.
  • Remove: a right-click option returns the item to storage with no loss.

9.3 Interfaces

RS3 furniture storage is a bank-like box outside the house, with no deposit or withdraw inside (document 1, section 6). The design copies that: a storage box and a workbench are spawned outside the Rimmington portal at start-up, and inside the house the build interface reads from the same stored counts.

Authoring pattern. A new interface is a numbered folder of component JSON files under cache-source/interfaces/ (the next free id is 1324), registered in the interface and component gamevals, with scripts in clientscripts/, opened server-side by interfaceManager.sendInterface(Interface.x) and handled by onButtonClick(Interface.x) in an @ServerStartupEvent function. The game-settings interface is the working example, and the estimate for a small interface is about a day. VERIFIED

Client state follows the project's varbit rule: a varbit only where the interface must own the value (for instance an "active session" flag), in the first free bit of the feature's parent varp after listing every varbit on it. The layout itself stays in the player save.

9.4 Crafting and limits

  • The workbench is an object with a tier (wooden up to requirement 20, steel framed up to 60, reinforced any). Crafting consumes materials, checks level (with saw and chisel boosts), grants XP and adds one unit to storage. Placement itself needs no level.
  • Limits follow RS3 as a data table: rooms 5/10/15/20/25 at levels 1/30/60/90/120; furniture 25/50/75/100/150/200/300/400/500 at levels 1/20/35/50/65/80/95/110/115; floors at levels 1, 30, 70.

9.5 Level 120

  • The stat packet sends the level as an unsigned byte, so 120 fits; the XP table enum 716 already has keys to 140, with key 120 equal to 104,273,167. CS2 does not clamp the level text. VERIFIED
  • Client work is cosmetic: stats_mouseover_create, xp_onstattransmit and stats_update special-case Dungeoneering (skill 24) and need a Construction case, so the tooltip and XP popup behave. VERIFIED
  • Server work: introduce Skills.getMaxLevel(skill) and replace the literal 99/120 sites: both getLevelForXp overloads, the target-level clamp, isMaxed, checkMulti99s, the "achieved 99" messages (three copies), the level-up check, Skillcapes.kt:65 and House.kt:381. About a dozen sites. VERIFIED Whether level 120 also changes the Construction cape and the max-cape rules is policy, not technical.

9.6 Functional furniture

The existing HouseController dispatches clicks on built-object ids in a long chain. Because furniture keeps its loc id after placement, these handlers keep working; they are re-expressed as @ServerStartupEvent plugins keyed by catalogue entry and stripped of any room assumption. Room-dependent handlers (the entry portal) become required fixtures with their own rules. Stairs are part of the room shell (section 5.2). Portal nexus, potion cauldron and tiered altars follow after the core loop.

10. Persistence and migration

10.1 Schema

HouseLayout(
  version   : Int = 2,
  rooms     : List<PlacedRoom>,        // shape key, cellX, cellY, floor, rotation,
                                       //   hasStairs, wallStyle, floorStyle
  furniture : List<PlacedFurniture>,   // id, x, y, floor, rotation   (tiles 0..47)
  doorways  : Map<String, DoorwayMode>,
  storage   : Map<String, Int>         // furniture id -> count owned and unplaced
)

All keys are stable strings, never enum ordinals and never renamed. The layout is a new nullable field on House; the legacy fields stay read-only until the migration is proven. The occupancy index is derived, transient, and never saved.

10.2 Legacy migration

The legacy grid is the new cell grid, so a 727 house can keep its layout:

  1. Each legacy RoomReference becomes a Square PlacedRoom at the same cell, floor and rotation, with the same style. Legacy dungeon rooms and staircase chunks are handled separately.
  2. Each ObjectReference(build, slot) is resolved to a tile by scanning the room's template chunk for the hotspot whose id is in build.ids and applying the room rotation. The hotspot table already exists: 816 hotspot rows across the 25 rooms, with chunk, tile and rotation. Multi-hotspot builds (windows, floors, hedging) produce one object per hotspot.
  3. Migration must read door positions and wall ids from the map, not from HouseRooms.doorDirs or WALL_IDS, because both disagree with the map.
  4. A build with no catalogue mapping is refunded into storage and logged.
  5. It runs once at login, writes the layout, and keeps a snapshot of the legacy fields for rollback.

Servants, pets and the portal location carry over unchanged.
